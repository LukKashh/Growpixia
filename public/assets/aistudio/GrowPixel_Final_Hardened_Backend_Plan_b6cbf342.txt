1. ATOMIC IDEMPOTENCY
Implement a correct database-backed idempotency mechanism for all economy mutations.

Critical concurrency requirement:
A SELECT ... FOR UPDATE cannot lock a row that does not exist. Do not use “select missing key, then insert” as the concurrency guard.

Use a database UNIQUE constraint and an atomic INSERT ... ON CONFLICT claim. Ensure the idempotency claim, economy mutation, and stored result occur in one PostgreSQL transaction.

Required behavior:
- Same idempotency key + same authenticated player + same operation type + same canonical payload, including simultaneous requests: exactly one economic mutation occurs; every identical caller receives the same successful stored result.
- Same key with a different player, operation type, or payload: return HTTP 409 conflict; do not mutate economy data.
- A retry after a completed operation returns the stored result and does not mutate again.
- Do not expose an intermediate “processing” response as a conflict for a concurrent identical request. PostgreSQL transaction/unique-conflict behavior must serialize the competing claim and let the second request read the committed result.
- Do not create a separately committed processing claim or lease system.
- Store enough data to validate the key scope and replay the original result.
- Use a globally unique key scope if the requirement is that reusing a key for another player or operation must be rejected. Otherwise, document and enforce the exact scope. The implementation must satisfy the mismatch-conflict requirement above.
- Ensure all economy changes and the idempotency result commit or roll back together.
- Handle database errors explicitly. Never report success if the transaction did not commit.

2. CANONICAL PAYLOAD SERIALIZATION AND HASHING
Create one shared server-side canonical serialization utility and use it for every economy operation.

Required interface:
toCanonicalString(payload: unknown): string

Requirements:
- Recursively sort object keys in deterministic lexical order.
- Preserve array order.
- Produce deterministic representations for supported JSON values.
- Reject NaN, positive/negative Infinity, undefined, functions, symbols, circular references, and unsupported object types.
- Reject Date, Map, Set, class instances, and other non-plain objects unless explicitly converted to a supported plain JSON representation before canonicalization.
- Normalize negative zero consistently.
- Use deterministic number serialization.
- Reject unsafe integer values for economy quantities and integer currency values.
- Do not silently coerce invalid values to null, strings, or zero.
- Hash the canonical string using SHA-256 on the trusted server.
- Never trust a hash supplied by the browser.
- Bind the authenticated player UUID, operation type, item/product ID, quantity, world/position when relevant, server-calculated price/reward, and every other parameter that can affect the mutation into the canonical payload.
- Use the same canonicalization implementation across store purchases, drop collection, block placement, and every other economy mutation.

8. REAL SUPABASE INTEGRATION TEST SUITE

The integration suite must cover:

A. Idempotency and concurrency
- Submit two simultaneous identical requests with the same key.
- Verify exactly one economy mutation occurred.
- Verify both callers receive the same successful result.
- Verify the second caller does not receive a transient processing conflict.
- Reuse the same key with a different payload; expect HTTP 409 and no mutation.
- Reuse the same key with a different player; expect HTTP 409 and no mutation.
- Reuse the same key with a different operation type; expect HTTP 409 and no mutation.
- Retry a completed request; verify the stored result is returned and no second mutation occurs.

- Nested object key order does not affect the result.
- Array order does affect the result.
- NaN, Infinity, -Infinity, undefined, functions, symbols, circular references, unsupported objects, and unsafe economy integers are rejected before RPC invocation.

C. Transaction rollback
- Force a failure after the Gems mutation is attempted but before the inventory mutation/result completion.
- Verify Gems, inventory, and idempotency state all roll back.
- Retry with the same key after the failed transaction; verify it can complete successfully.

- Invalid token rejected.
- Missing token rejected.
- Body/query token rejected.
- Missing or inconsistent profile rejected.

- service_role can execute the intended server-side RPC.
- No service key appears in built client assets or source maps.

E. Player data loading

- Valid player with zero Gems and empty inventory.
- Missing profile.
- Malformed RPC response.
